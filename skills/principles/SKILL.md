# Principles — 工程原则参考

> 本文件由 `kalandramo/pstack` 的 24 条 `principle-*` 技能合并聚合成单篇参考，同作者，遵循 MIT。原每条原则是独立技能，这里聚合为单篇以避免 24 个技能同时占表面积。dev / loop / go-gate / refactor 在相应阶段引用本文件的具体条目，不重复展开。

## 设计（Design）

### model-the-domain（领域建模）
用数据结构表达真实领域，而不是散落在条件判断里。状态机替代散落的布尔/阶段标记；类型化模型替代松散参数；映射/判别联合替代跨文件分支；reducer/命令-事件模型替代临时变更。写时选型成本低，事后挽回读作重构。不要强行抽象——当前形态已清晰、局部、不太会增长时，用无聊代码（boring code）。

### foundational-thinking（基础优先）
先定数据结构再写逻辑；收敛核心类型，显式优于聪明。并发前先问「另一参与者并发改它会怎样」。脚手架（CI/lint/测试/共享类型）先行；提交小且单一目的。每个增量落一个内聚抽象或深化已有者，勿把新能力摊成调用方的特例协调。减法先于脚手架：先删死代码再打地基。

### exhaust-the-design-space（穷尽设计空间）
面对代码库无先例的新交互/架构决策，先建 2–3 个互相竞争的原型并排比较再下定论。也适用于体验驱动（非逻辑驱动）的产品决策。

### redesign-from-first-principles（第一性原理重设计）
整合新需求时不要外挂到旧设计，而是假设该需求从一开始就是基础假设来重设计；把改动传播到所有引用（类型/文档/示例/理由）；先想全盘再增量交付。区别于 attack-the-premise（后者质疑当前设计假设的事实，而非围绕新需求重建）。

### experience-first（体验优先）
实现便利与用户愉悦冲突时选愉悦。每个功能/控件/选项都要有理由；少而精优于多而糙；先用可丢弃原型验证；把细节（过渡/对齐/间距/反馈/错误态）做对。消费方包括终端用户、导入你代码的同事、以及下一个维护者，同等权衡并以他们的视角解释影响。

### boundary-discipline（边界纪律）
校验/类型窄化/错误处理放在系统边界（CLI 参数、配置文件、外部 API、网络协议）；内部无条件信任类型，业务逻辑在纯函数里，壳层薄而机械。边界解析为领域类型后不外泄传输/存储/框架/线类型；边界内不重新校验已校验的数据。

## 实现（Implementation）

### type-system-discipline（类型系统纪律）
让编译器拒绝不可能状态、错配原语、未处理变体。给语义原语打标（UserId/OrderId 不可互换）；外部数据在边界 parse 成类型化模型；类型从权威 schema（protobuf/OpenAPI/GraphQL/migration/design-token）派生。详见本文件 encode-lessons-in-structure。

### minimize-reader-load（降低读者负担）
可维护性 = 读者理解代码所需的工作量，两个独立轴：要追的层数（间接层）与要记的状态（隐藏/可变上下文）。折叠只调用一次的包装、无第二实现的适配器、投机性间接层；收窄状态作用域（纯函数 > 局部 > 字段 > 模块 > 全局）；在边界命名不变量而非每个消费者。新读者应能在 30 秒内回答「X 从哪来 / 什么能改 X」。

### build-the-lever（造杠杆）
非平凡工作先造工具完成或证明它（codemod/脚本/生成器），而不是手工做。工具是可重跑产物，也是审查者能复核的工件。先手工做一遍单元学套路，再造工具并对拍验证。确定性杠杆胜过扇出；应用本原则应产出文件，若引用了却 diff 里没有工具等于没用。会话外的活计，提交杠杆。

### encode-lessons-in-structure（把教训编码进结构）
反复出现的指令/纠正 → 编码成 lint、元数据标记、运行时检查或脚本，而不是更多文字。若教训需要判断力无法编码，则把指令前置并举例失败模式。若修复是结构性的，只用结构性修复——指令只是症状。

## 验证（Verification）

### prove-it-works（证明它有效）
每次产出都直接核对真实产物：查进程存活而非派生状态，读真实值而非缓存/派生表示。验证失败时先怀疑观测方法再怀疑系统。最强证明是可重跑的确定性脚本，其输出作为审查者能重跑的工件；大/复杂工作才提交证据工件。

### explain-the-number（解释数字）
跑之前先写决策：会改决策的结果是什么、噪声地板在哪；当 run-to-run 散布大于效应就停。问「为什么不是两倍好」——从 profile/系统计数找出限制因素（核/锁/盘/网/负载生成器）并映射到源码，只读代码猜的不算限制。列出数字还可能测的别的并逐一用证据排除。把运行次数/散布/限制因素留在记录里。性能数走 benchmark 流程；eval 结果对每个 trial 问同样的问题。

### test-behavior-not-implementation（测行为不测实现）
测试是对用户（调用方/终端用户/其他服务）能观察行为的声明。对每个测试做两个想象编辑：破坏行为（若仍通过则证明不了什么）；改内部实现保持可观察结果不变（若失败则绑死实现）。保留前者、存活后者的测试；其余重写或删。契约决定断言，而非断言形状。

### attack-the-premise（攻击前提）
两个及以上共享同一前提的修复都倒在同一个门禁时，怀疑前提而非修复。写下前提（每轮失败修复都假设的那句话），在下个修复前测前提；看失败如何分布而非多大。矛盾则原因在别处；吻合则追问下一个「为什么」（见 fix-root-causes）。移除条件而非补偿它。

### fix-root-causes（修根因）
调试时修故障首次发生处，而非浮现处。先复现，每步追问「为什么」直到答案是代码里的错误决策；卡住就插桩读真实错误与状态。若触发症状的状态合法，则在破裂处处理它（这才是根因）；若状态本不该存在，在破裂处加检查只会藏 bug，去找产生该状态的源头。仅重启后才失败 → 先疑持久化状态（配置/缓存/锁/序列化状态）。找相同故障的所有位置一并修。需一长段注释 justify 的 workaround，说明代码错了。

## 重构（Refactor）

### subtract-before-you-add（先减后加）
演进系统时先删复杂度再建。持续投资简化：留比进来时更简单、更强能力的设计。删先于建、削先于磨；为观测到的用法而非投机边界设计；除 spec 要求外不加投机校验/解析/守卫；简化提示词；无新内容的引用直接删而非留桩。

### laziness-protocol（懒惰协议）
重构/评估 diff 大小/想加抽象时偏向删除、偏向最小改动。合并决策：同一选择不要散在多处的重复，收到单一真相后传简单标志。

### migrate-callers-then-delete-legacy-apis（先迁调用方再删旧 API）
新内部 API 替换旧调用方时，在同一波里迁移调用方并删除旧 API，不留兼容层。适用：无外部用户依赖向后兼容、项目能吸收协调式破坏性变更、新 API 属简化/重构计划。更新测试断言新契约、删只保护重构前实现细节的测试。

## 并发（Concurrency）

### separate-before-serializing-shared-state（先分离再串行化共享状态）
并发参与者可能共享可变状态时，先问是否需要同一个可变对象；不需要就消除共享。默认给每个参与者自己的文件/键/分支/状态目录，只在读取/汇报边界合并（两人写各自 lastX 进同一 state.json 仍是共享变更）。仅当单一共享写者是真实不变量时，才用锁文件/顺序阶段/单一写者/原子 CAS 做结构性串行化；「需要锁」当作要检查的设计气味而非默认答案。指令和约定不是并发控制。

### make-operations-idempotent（让操作幂等）
设计操作无论跑多少次、上一轮在何处崩都收敛到正确终态。每步从「当前存在的状态」推导，而非「上一轮打算做什么」；只读当前状态比对目标，只应用差值。残留物（锁/临时文件/半写记录/认领的任务）必须能被下一轮判为陈旧——按「上一轮可能在任何点停」都成立的证据判，而非只看常见情况。测试：连跑两次会怎样？在每点崩会怎样？重跑是否收敛同终态？

## 执行 / 循环（Execution & Loop）

### sequence-verifiable-units（把工作排成可验证单元）
工作排成小单元序列，每单元落到可检查状态，未绿不前进。扫荡/迁移/成批相似编辑中，每改一处先验证再下一处；每单元是「已知好态→一处改动→跑检查→前进」的括号。先 rebase 到干净主干，每查针对真实基线。杠杆做编辑时单元检查几乎免费，仍要跑。交付时按「审查者能重放」的顺序堆叠提交/PR（典型形状：失败测试在前，修复在其上）。是 prove-it-works 与 build-the-lever 的排序补充。

### outcome-oriented-execution（结果导向执行）
优化可验证的终态而非保留平滑的中间态。为计划好的重写/迁移保留中间断裂（需声明、可回滚、范围可控）；迁移中对活跃改动区保留高信号检查，计划完成时做完整静态+运行时验证。

### guard-the-context-window（守住上下文窗口）
上下文溢出会劣化推理、产生压缩伪影、停滞。按阶段限大小、设轮次预算、核算机制成本。

### never-block-on-the-human（别在人上阻塞）
人类异步监督，代理保持不被阻塞：做合理决策、推进、事后让人纠偏。代码改动可逆且可审，错决策通常比阻塞便宜。不可逆动作（强推/删生产数据/发外消息）仍须确认；可逆动作（写代码/改笔记/拆任务）不阻塞。产品方向来自人，执行不应阻塞。
