# dev — 单一入口的受控开发循环

一条需求进来，一路走到"可评审的分支"。用户不再需要在需求梳理、切片、循环、审阅、收尾这五件事之间手动接力——本技能把它们串成一条流水线。

## 三个承诺

1. **一个入口，自适应跳过与停止。** 有 PRD 就跳过设计阶段；需求一句话且单文件就跳过切片阶段；用户声明只要设计（或设计+切片）时，在对应阶段边界停止，不进入实现。不做"每次都走满六步"的形式主义，也不做"说了停还往下跑"。
2. **一个状态源，两本账各司其职。** `.dev/run.json` 记**流程状态**（走到哪个阶段、验收标准、本轮假设），`.dev/results.tsv` 记**判定账本**（每轮指标与判决，由 `loop` 维护）。恢复时读 `run.json`，引用指标时读 `results.tsv`，两者不互相覆盖。
3. **内层循环，不是批量队列。** 本技能对**同一个需求**迭代 N 轮（实现 → 门禁 → 审阅 → 判定）。一次只做一条需求；批量多任务、按依赖图并行编排不在本技能范围内。

## 与现有技能的关系

**编排层（本技能）** 决定"做什么、做到什么程度"；**能力层** 只被按需调用，不参与流程决策。

```
dev（本技能，内层循环）
  ├─ 阶段0 判据     → 读全局契约（AGENTS.md 架构条目 + .arch.json 层表），把架构约束落成一条验收标准
  ├─ 阶段0.5 诊断   → smell（存量模块改造，或 arch 报警后的局部 import 图分析，每需求最多 1 次）
  ├─ 阶段1 设计     → 选择题提问消歧 + 产出一份合并设计文档，存 tasks/（架构节引用全局层表，不重画）
  │                   └─ stop_after=design：文档落盘即停，进阶段 7
  ├─ 阶段2 切片     → 内联做纵向切片，产出写入 .dev/tasks/（不强制建 Issue）
  │                   └─ stop_after=slicing：产出落盘即停，进阶段 7
  ├─ 阶段3 实现     → 先看层表再动手；modern-go 索引（仅 .go）；typescript 纪律（仅 .ts/.tsx）
  ├─ 阶段4 门禁     → go-gate（含 arch 分层判定）/ ts-gate，按改动语言择一，是验证与指标的唯一来源
  ├─ 阶段5 审阅     → 独立子代理读 diff + 全局契约；越界依赖（arch_drift）直接 blocking
  ├─ 阶段6 判定     → loop（epsilon 比较、keep/revert、停止条件）
  └─ 阶段7 收尾     → 对账设计文档与全局契约；默认停在分支，用户明确要求时才推送或开 PR
```

三者职责严格分离，任何一种都不能替代另一种：`go-gate` 回答"这版对不对"，`loop` 回答"这版要不要留、还继续吗"，`dev` 回答"接下来做什么"。判据与验证分离后，加一门语言只需照着同一份契约再写一个门禁脚本（`ts-gate` 就是这么来的），判定逻辑不动。

上游 goal-workflow 的 `review-it` 依赖宿主内置的 `/review` 类命令，WorkBuddy / ZCode / Qoder 都没有，所以本仓库没有收录它。本技能因此内置"自包含审阅"（阶段 5）：派独立子代理读 diff，不依赖任何外部命令。

### 指导原则（参考 `principles` 技能）

本技能在关键阶段默认遵循 `principles` 技能里的工程原则，不重复展开：

- **阶段 0 / 规划**：`foundational-thinking`（先数据结构/脚手架）、`model-the-domain`（领域建模）、`exhaust-the-design-space`（无先例时多原型对比）。
- **阶段 3 实现**：`subtract-before-you-add`（先删后加）、`build-the-lever`（造工具而非手工）、`minimize-reader-load`（降读者负担）。
- **阶段 4 / 5 门禁与审阅**：`prove-it-works`（核对真实产物而非自报）、`test-behavior-not-implementation`（测行为不测实现）、`boundary-discipline`（边界校验）。
- **阶段 6 判定**：`sequence-verifiable-units`（单元可验证）、`explain-the-number`（性能数字先解释再信）。
- **全程**：`never-block-on-the-human`（可逆动作不阻塞）、`guard-the-context-window`（上下文预算）。

需要某条的展开说明时，读 `principles` 技能对应条目。

## 上下文预算：能力层必须按需加载

`modern-go` 1139 行、`smell` 750 行、`refactor` 716 行，合计约 35k tokens。**任何一轮循环都不允许全量加载它们**，否则第一轮就会耗尽上下文，后续轮次只能靠猜。

| 技能 | 何时读 | 读多少 | 怎么读 |
|---|---|---|---|
| `modern-go` | 阶段 3，且本轮改动含 `.go` 文件 | 只读索引（30–46 行） | `modern_index.sh --root <repo>`；命中后 `--section <起始行>` 抽那一节（约 30 行） |
| `refactor` | 阶段 5，且审阅提出结构性 blocking | 只读对应手法一节 | `grep -n '^### ' refactor/SKILL.md` 定位，再按行号抽节 |
| `smell` | 阶段 0.5（存量改造，或 `arch` 报警后局部诊断）；或阶段 7 收尾体检 | 全量，但**每需求最多 1 次** | 一次读完，产出报告后即卸载，不留在后续轮次的上下文中 |

判断标准很简单：**本轮的假设用不到某技能，就不要读它。** 读进来却没用上，等于用上下文预算买了一份没看的说明书。

## 阶段 0：把需求变成判据

在任何编辑之前完成，产出写入 `.dev/run.json` 并向用户复述一次。

```json
{
  "version": 1,
  "requirement": "原始需求原文",
  "carrier": "local",
  "base_branch": "master",
  "branch": "dev/add-lru-cache",
  "stop_after": null,
  "doc_path": null,
  "rounds_max": 5,
  "rounds_done": 0,
  "phase": "criteria",
  "metric": {
    "name": "ns_per_op",
    "direction": "lower",
    "baseline": null,
    "best": null,
    "target": null,
    "epsilon_pct": 1.0
  },
  "criteria": [
    { "id": "C1", "text": "命中率 ≥ 80%", "verify": "go test -run TestHitRate", "done": false },
    { "id": "C2", "text": "现有测试全绿", "verify": "go test ./...", "done": false },
    { "id": "C3", "text": "不新增跨层依赖（遵守 .arch.json）", "verify": "bash <plugin_root>/skills/go-gate/scripts/gate.sh --skip build,vet,test,race,lint,bench", "done": false }
  ],
  "history": [],
  "updated_at": "2026-11-13T16:00:00+08:00"
}
```

规则：

- **每条验收标准必须绑定一个可执行验证方式。** 写不出 `verify` 的条目退回给用户澄清，不得留空冒充。
- **`rounds_max` 默认 5。** 用户明确指定时以其为准。
- **`stop_after` 默认 `null`**（走满全流程）。合法值只有三个：`null` / `"design"` / `"slicing"`，分别表示"走满" / "阶段 1 产出后停" / "阶段 2 产出后停"。只有用户显式声明"只要设计""出设计文档就停""先别实现"等意图时才设置，不得自行推断；其它值视为非法，退回澄清。停止点只能是阶段边界，不支持在阶段中途停。
- **`metric` 可为空对象**（无 benchmark 的项目）；此时 `metric.baseline` 保持 `null`，全流程不得出现"性能提升"的表述。
- **`doc_path` 默认为 `null`**，指向阶段 7 文档同步要对账的设计文档。取值规则：
  - 用户在需求里显式指定路径（如"同步 `tasks/rate-limiter-design.md`"）→ 校验文件存在且含三大部分，然后写入；不存在或非设计文档则退回澄清，不猜测。
  - 用户未指定但 `tasks/*.md` 中有候选 → 列出候选让用户选择，**不得自行推断**（对账哪份文档是方向性决策）；用户说"你定"时保持 `null`。
  - 本次阶段 1 产出新文档 → 由阶段 1 写入路径（见 1b）。
  - 典型场景：第一次 dev 开发功能、第二次 dev 做性能优化并回写原功能文档——第二次在需求里指定 `doc_path`，不必重跑阶段 1。
- **任务载体自动探测**：`gh auth status` 成功且有 `origin` 远程 → 需求可能来自 GitHub Issue（`gh issue view <N>`）；否则从 `.dev/tasks/*.md` 或用户输入读取。写回 `carrier` 字段。

### 0a. 先读全局契约（在任何编辑之前）

判据不能凭空造：项目的分层规则、包边界、禁止依赖散在三处，开工前一次读完。读不到就记"无"，不要假装读过。

| 位置 | 读什么 | 用途 |
|---|---|---|
| `AGENTS.md`（项目根） | 规则化条目：架构约定、禁止的依赖、易错配置 | 转成验收标准；收尾也写回这里（见"经验沉淀"） |
| `.arch.json`（或 `--arch-config` 指向的文件） | 层表 + allow 矩阵 + forbid + strict | 直接决定 `arch` 门禁能否过；缺失时先判形态：目录即层用 `--init`，目录是业务切片或只写在文档里用 `--evidence`（见下） |
| `tasks/*-design.md` 第三部分 | 既有模块的层表、接口口径 | 新需求**沿用**它，不要拿"当前代码现状"重新描述架构 |

规则：

- **没有契约文件不等于没有契约。** 项目里已有明显分层（`internal/domain`、`internal/app`、`internal/infra` 之类）却缺 `.arch.json` 时，用一次选择题问用户是否落一份；用户说"你定"就按形态取（目录即层用 `--init`，**不要手写，也不要凭想象编层表**），把"反向依赖清单里保留 / 清理了哪几条"记进设计文档的"待解问题"。跳过这一步的代价是：之后每一轮都只能靠审阅者主观判断分层，而模型的"常识分层"与项目的实际约定往往不是一回事。
- **目录不按层切的项目要读文档，别硬套目录惯例。** 先一句话判形态：`ls internal` 出来的是 `domain / app / infra` → 目录即层；出来的是 `order / user / billing` 且每个下面又有 `domain / infra` → 目录是**业务切片**，层在深度 2。后者（以及层只写在文档里的项目）用 `check-arch.py --evidence` 取事实清单——分组与包数、真实 import 方向、在多个父路径下重复出现的目录名、`README` / `AGENTS.md` / `docs` 里提到分层的行（带 `文件:行号`）——再据此写 `.arch.json`，切片用通配前缀 `internal/*/domain` 那种写法，新切片自动纳管。
- **模型可以写契约，但未经自检的契约不许生效。** 写完必须跑 `check-arch.py --verify`：前缀匹配不到任何包 = 规则永不触发；一个包同时命中多个层 = 语义含糊；有包不属于任何层 = 新包会绕过判定。前两条是 FAIL，必须改到过。假契约比没有契约更坏：没有契约时人知道自己在裸奔，假契约让人以为有保护。`--init` 生成的初稿同样要过 `--verify`。
- 契约存在时，`criteria` 必须有一条专管它（见上方 `C3` 示例）。这样门禁红了是"某条验收标准没过"，而不是一句可以商量的"建议改进"。
- **契约优先于代码现状。** 契约说 domain 不依赖 infra、代码早就依赖了 → 把冲突写进"待解问题"，不在实现阶段顺手清历史欠账（那是独立 `refactor` 轮次的事）。
- **`--init` 的初稿只翻译目录惯例**：`allow` 只写外层→内层，代码里现存的反向依赖不进 `allow`，而是作为"需人工定夺"清单列出（带文件:行号）。这份清单必须逐条看——确认是欠账就在本需求之外单独立项清理，确认是合法方向才加进 `allow` 并写理由。直接把初稿提交，等于用工具给漂移盖章认证。

向用户复述的格式：

```
需求：<一句话>
验收：C1 <...> → <verify>；C2 ...
门禁：go-gate | ts-gate（race=<是/否>, bench=<pattern 或 关闭>, arch=<.arch.json 的层数 或 无契约>）
循环：N=5 轮，指标 <name> 方向 <lower/higher> 基线 <值或"未度量">
停止点：<走满全流程 | 设计后停（产出一份合并文档 tasks/<id>-design.md） | 切片后停（产出 .dev/tasks/<id>.md）>
对账文档：<doc_path 或"本次阶段 1 产出"或"无（不回写已有文档）">
全局契约：<.arch.json N 层（含 K 个通配前缀）+ AGENTS.md K 条架构条目 | 无（已按现状落一份 / 待用户确认）>
出口：dev/<slug> 分支，不推送不合并
```

## 阶段 0.5：存量模块诊断（可选；改造类需求，或 arch 报警后）

**触发条件**（满足任一，两者共用"每需求最多 1 次"的额度）：

1. 需求是对**已有模块**做改造/重构，且该模块文件数 > 5。
2. `arch` 门禁报警（跨层 import / 未分层新包），且涉及 ≥ 2 个包：此时从阶段 4 回跳到本阶段（仅 1 次），只取报告里的 Dependency Analysis，对**受影响的包**做局部 import 图分析，用来确定"把依赖倒过来"的具体切法，不受文件数 > 5 限制。

**不触发**：新功能、单文件修改、纯 bug 修复，**且** `arch` 未报警。跑一次 `smell` 要通读模块，代价远高于本轮收益。

触发时调用 `smell`，产出写入 `.dev/smell.md`，只取其中两样：

1. **轮次候选清单**：把报告里的 Critical 与 Immediate Actions 转成"每轮一个假设"的候选，写进 `run.json` 的 `history` 预排。
2. **不可在本需求内修的项**：明确列入阶段 7 报告的"未解决"，避免循环跑到一半才发现方向超出范围。

**约束**：每需求最多诊断 1 次。报告落地文件后即视为已消费，后续轮次**不得重新通读源码复述坏味道**——需要时读 `.dev/smell.md`。由 `arch` 报警触发的局部诊断同样计入这一次额度，只扫受影响包，**不得**据此下全量架构结论。

架构坏味道通常不是单轮能消除的，所以本阶段的作用是**定位与排序**，不是"一次性修完"。

## 阶段 1：设计（可跳过）

**跳过条件**（满足任一）：需求已在 PRD/SPEC 中存在；改动预计 ≤ 2 个文件；用户在需求里已给出实现方案。

否则执行下面的流程。**本仓库不收录专门的 prd / spec 类技能**，设计文档由本阶段内联产出，不要让用户去装别的技能。

### 1a. 提问消歧（写文档之前）

先澄清需求再动笔，不要自行决定。按需求复杂度提 2–8 个**选择题**（每题带 A/B/C/D 选项，用户可用"1A, 2C"速答）；能从用户原始输入里看出的维度直接跳过，不为凑数提问。简单功能 2–3 题，典型功能 3–5 题，多角色/跨系统的复杂功能 6–8 题。一次只问一个问题或一批选择题，等用户回答后再进入 1b。

**逃生口**：用户说"你定"/"按常规"/"跳过提问"时，按合理假设直接写，不阻塞；但必须把所有自行做的假设列进文档的"待解问题"章节，让用户事后能看到并纠正。**涉及破坏性变更或难以回退的方向决策不得跳过确认**——这类决策必须拿到用户明确答复才动笔。

### 1b. 一份文档，三大部分

每个功能只产出**一份**合并设计文档，存 `tasks/<id>-design.md`（`<id>` 用需求的短横线 slug），写入 `run.json.doc_path`——阶段 7 的文档同步据此对账，无需再猜路径。不拆成 prd/spec/design 三份——一份就够看清功能全流程。文档内部用三个独立章节隔开，**严禁部分之间内容交叉**：第一部分管"做什么"，第二部分管"为什么选这条"，第三部分管"怎么建"。

**专有名词中英文对照**：用户可能不熟悉英文专有名称，文档必须给出中文译文，不能只写裸英文。规则如下：

1. **术语表**：文档开头（第一部分之前）放"术语表"，三列——中文 / 英文缩写 / 英文全称或说明。覆盖全文所有专有名词，供读者随时回查。简版文档也要——只要出现专有名词就建，哪怕只有三行。
2. **覆盖范围**：三类均须收录——① 产品/技术缩写（PRD、SPEC、RFC、API、ADR、RBAC 等）；② 领域业务术语（本项目/本系统的实体、角色、流程名）；③ 项目工作流术语（US-N、FR-N、tracer bullet、baseline、keep/revert 等）。
3. **首次出现**：任何英文专有名词首次出现必须带中文译文，格式统一为 `中文（English 缩写, English 全称）`，例：`产品需求文档（PRD, Product Requirements Document）`、`基于角色的访问控制（RBAC, Role-Based Access Control）`。禁止只写裸英文缩写。
4. **后文**：允许直接用缩写（如 `RBAC`、`FR-002`），前提是术语表能查到；不要求每次重复中文，避免拖慢阅读。

**代码引用口径**：文档与报告中的代码/路径引用按三种性质处理，不一刀切：

| 性质 | 出现位置 | 写法 |
|---|---|---|
| **证据 / 评审报告** | 审阅发现、回滚理由、门禁失败日志、收尾报告 | 坐标就是内容，绑定当时的 rev 冻结：写 `main.go:1134 @ <rev>`，报告头部声明"代码基线：`<branch>@<rev>`"。读者要复现就 checkout 那个基线。死链不用修——修了等于把历史改写成现在，反而失真 |
| **活文档**（设计稿、架构图） | `tasks/<id>-design.md` 的设计与契约章节 | 留路径、别留行号：写 `session/store.go` 的 `Evictor`，不写 `store.go:78`。路径变更频率远低于行号，导航寿命更长 |
| **契约**（层表、接口口径） | 第三部分的实现契约、层表 | 尽量不写坐标：包名、接口名、端点名就够，口径不依赖代码布局 |

**降级判据**：维护成本超过导航价值时，引用降级为「rev + 符号」，不再回填路径。路径存在且稳定就留路径；路径频繁变动或已不存在时只保留 `rev + 符号`，让读者 checkout 那个基线自行定位。不要为了"精确"在活文档和契约里补行号。

#### 第一部分：产品需求（what / why，必写）

按以下九段写，全部必写：

1. **概述**：功能一句话说明 + 背景。
2. **目标**：要达成的结果，可衡量。
3. **用户故事**：按 `US-001` 编号，每条带验收标准。验收标准必须**可观察、可测试、可验证**三者之一；"运行正常""体验良好"这类空话一律重写；涉及 UI 的故事强制带"在浏览器中验证"。
4. **功能需求**：按 `FR-N` 编号，**每条只描述一个行为**，不许用 and 把多个行为塞进同一条。
5. **非目标**：明确不做的事。
6. **设计考量**：影响设计的产品约束。
7. **技术考量**：已知的技术约束。
8. **成功指标**：怎么算成功。
9. **待解问题**：未决事项 + 1a 中所有自行做的假设。

#### 第二部分：设计取舍（why / which，骨架必写，按触发展开）

以 Go proposal 风格写。必写骨架：**Abstract（摘要）、Design（设计）、Rationale（理由与取舍）**。灵魂是 Rationale：**必须主动列出至少一个被放弃的备选方案，以及放弃它的原因**——"我们没选 X，因为 Y"。这比单方面论证所选方案更可信，也让后来人不必把同一场争论再吵一遍。

按条件展开其余章节：

| 条件 | 展开章节 |
|---|---|
| 存在破坏性变更 / 难回退的改动 | **Compatibility（兼容性）**：开门见山承认代价，给出渐进迁移路径 |
| 有真实的方案岔路（2 个以上做法都说得通） | **Alternatives（备选方案）**：逐个列出并说明取舍，与 Rationale 呼应 |
| 有明确的实现步骤与验证方式 | **Implementation（实现与过渡）**：用实测数据或自动化工具支撑"可落地" |
| 借鉴了业界既有做法 | **Prior art（既有实践）**：别人怎么解决同一问题 |

可以写多个候选方案再选一个，但**不要为展示能力硬凑方案**；方向已清楚时写一版做完比摆三个半成品有用。

#### 第三部分：实现契约（how，按复杂度分级）

这一部分的长度随需求复杂度伸缩，简单功能不堆篇幅：

| 复杂度判据 | 写法 |
|---|---|
| **简版**：单文件改动、无新 API、无新数据表 | 架构一句话 + API 要点 + 数据模型要点，几段即可，不展开全部小节 |
| **全量版**：多角色 / 跨系统集成 / 新数据表 / 多 Agent 并行实现 | 展开下列十节，给到字段级精度 |

全量版十节：**摘要、架构、数据模型、API 设计、业务逻辑、错误处理、安全、性能、测试策略、实施计划、开放问题与风险**。其中：

- 数据模型给出建表 SQL 与实体定义；
- API 设计列出每个端点的方法、路径、鉴权、请求响应结构、错误码；
- 测试策略包含**映射表**：每条 US-N 的验收标准至少对应一个测试用例，每条 FR-N 落到某个 API 端点或业务规则；
- **质量红线**：不许出现 TBD/TODO——要么现在解决，要么明确挪进第一部分的"待解问题"；不要复述第一部分的内容，这一部分只增加技术深度。
- **架构一节引用全局层表，不重新描述。** 写"沿用 `.arch.json` 的 N 层；本次新增包 `x` 归 `domain` 层；新增允许边 `app → foo`"。另起一段重新画架构，等于制造第二份契约，两份必然漂移。

#### 文档质量闸门

文档写完后自检，任何一条不满足就重写对应段落：

- [ ] 三个部分齐全，且没有互相复述；
- [ ] 每条 US-N 有可观察/可测试/可验证的验收标准；涉及 UI 的有"在浏览器中验证"；
- [ ] 每条 FR-N 只描述一个行为；
- [ ] Rationale 至少有一个被弃方案及原因；
- [ ] 第三部分没有 TBD/TODO，每条需求都落到 API 端点或业务规则；
- [ ] 术语表存在（简版同样适用）且覆盖全文所有专有名词，含三类：产品/技术缩写、领域业务术语、项目工作流术语；
- [ ] 每个英文专有名词首次出现均带中文译文，格式为"中文（English 缩写, English 全称）"，无裸英文缩写；
- [ ] 后文出现的缩写均已在术语表登记，格式统一；
- [ ] 代码引用符合三种性质：设计文档（活文档）只留路径 + 符号、不写行号；契约章节只写包名/接口名/端点名，不写坐标；确需坐标的证据类引用绑定 rev。

### 1c. 确认闸门

文档落盘后**向用户呈现并请求确认**。确认的语义随 `stop_after` 变化：

| stop_after | 确认的内容 | 确认后动作 |
|---|---|---|
| `"design"` | 只确认**文档写得对不对**，不存在"放行实现"这回事 | 直接进入阶段 7 提前收尾，不进阶段 2/3 |
| `null` / `"slicing"` | 确认文档 + 放行后续阶段 | 进入阶段 2（slicing 继续到阶段 2 后再停） |

用户说"OK"/"确认"/"继续"才放行后续动作；用户要求修改的，改完重新确认。

**逃生口**：用户说"你定"/"直接继续"时视为确认，但文档中的"待解问题"章节必须完整列出所有自行做的假设。这与 `never-block-on-the-human` 原则一致——设计文档是可逆的中间产物，允许先写后改；但破坏性变更的方向决策已在 1a 强制确认过，不在此处放行。

不要在阶段 1 写业务代码。

**停止检查**：1c 确认通过后，若 `stop_after == "design"`，将 `run.json.phase` 置为 `"stopped"`，写入 `stopped_at: "design"` 与 `stop_reason: "stop_after=design"`，**直接进入阶段 7**（走"提前停止"分支），不进阶段 2/3。此时无验收标准被执行，`criteria.done` 保持 `false` 是正常状态，不视为失败。

注意顺序：跳过条件与停止检查独立。若因"用户已给方案"跳过阶段 1 且 `stop_after == "design"`，则没有设计文档可交付——回到阶段 0 向用户澄清（他要的设计文档对应哪个阶段产出），不要空手进收尾。同理，1c 的确认闸门未通过前，即使 `stop_after == null` 也不得进入阶段 2。

## 阶段 2：切片（可跳过）

**跳过条件**：整个需求能在一个上下文窗口内完成，且验收标准 ≤ 5 条。

否则自行做纵向切片（tracer bullet）：每片落地即可演示，而不是"先建表、再写 API、再做界面"。产出写入 `.dev/tasks/<id>.md`，每片带 `verify` 命令。`rounds_max` 分配给各片时，单片至少 1 轮。

**停止检查**：切片产物落盘后，若 `stop_after == "slicing"`，将 `run.json.phase` 置为 `"stopped"`，写入 `stopped_at: "slicing"` 与 `stop_reason: "stop_after=slicing"`，**直接进入阶段 7**（走"提前停止"分支），不进阶段 3-6。若阶段 1 因跳过条件未产出设计文档，而用户指定的是 `slicing`，那也照常停在此处，报告中如实列出阶段 1 被跳过的原因。

## 阶段 3-6：内层循环

对 `round = 1..rounds_max` 重复。**每轮只允许一个可判定的目标**，写在 `run.json` 的 `history[round].goal`。

| 轮次 | 默认目标 | 判据 | 说明 |
|---|---|---|---|
| 1 | `feature` | 全部验收标准达成 | 实现阶段 0 定义的功能 |
| 2..N | `perf` | 指标优于最优 ≥ epsilon | 需 `--bench`，否则不得标记为本目标 |
| 2..N | `coverage` | 覆盖率上升且测试全绿 | 覆盖率的"上升"必须是新增真实断言，不是加 `if true {}` |
| 2..N | `robustness` | 新增的失败用例从红转绿 | 先写能复现问题的测试，再修 |
| 2..N | `refactor` | 测试全绿**且**指标不退化 | 行为不变，只改结构 |

`refactor` 目标的特殊性：它**不产生新能力**，价值在于降低下一轮的修改成本。因此它的判据里没有"改善"要求，只有"不退化 + 测试守住行为"。若 refactor 后指标劣化超过 epsilon，照常 `REVERT`——"结构更好所以要容忍变慢"不成立，两者分开记账。

### 3a. 声明本轮假设

一句话，可证伪：`"热点在 Concat 的字符串拼接，改用 strings.Join 可降 30% 以上"`。写不出单一假设 → 停止循环，说明需求应拆分为多个任务。

### 3b. 实现

- 只改与该假设相关的代码；不改无关代码、不顺手重构、不改测试断言。
- **动手前看层表**：本轮新增或修改的 import 必须落在 `.arch.json` 的 allow 矩阵内。确需新方向 → 先改契约（`.arch.json`）并向用户说明理由，不要在代码里绕过去再让门禁背锅。**新建的包必须先在层表里定层**，否则 `strict.require_layer_under` 会直接判为未分层。
- 改动文件数 > 5 时停下来复核假设粒度，通常意味着应该退回阶段 2 切片。

**涉及 `.go` 文件时，先看索引再动手**，不要把 1139 行规则整份读进来：

**涉及 `.ts` / `.tsx` 文件时，先读 `typescript` 技能的类型纪律**（判别联合、品牌类型、边界校验、避免 `as` 强转等），其下的 `references/patterns.md` 有每条规则的代码示例。前端 / UI 任务落地后，用 `writing` 技能的 §3（Impeccable，`npx impeccable detect`）做最后一道去 AI 味闸门。

```bash
bash <plugin_root>/skills/modern-go/scripts/modern_index.sh --root <repo>
# 输出：项目 Go 版本、46 条规则中当前版本可用/不可用的清单（含行号范围），约 40 行
# 命中某条后只抽那一节：
bash <plugin_root>/skills/modern-go/scripts/modern_index.sh --section <起始行>
```

规则：
- **版本门控是硬约束。** 索引里列在"不可用"的规则一律不得使用——那会让代码在项目声明的 Go 版本上编译失败。
- **只应用与本轮假设相关的规则。** 顺手把整个文件现代化会污染 diff，让下一轮无法归因。
- **语义变更类规则只建议不自动应用**：`math/rand/v2`（随机流改变）、`iter.Seq`（API 形状改变）、`os.Root`（错误路径改变）。在报告里列出，由用户决定。
- 若项目无 `go.mod`，索引脚本会返回 rc=2，此时向用户确认目标版本，不要默认按最新版改。

### 4. 门禁

按本轮改动的语言选门禁，**不要两种都跑**——另一语言的门禁会全量扫描无关代码，既慢又引入噪声：

| 项目类型 | 命令 |
|---|---|
| Go（有 `go.mod`） | `bash <plugin_root>/skills/go-gate/scripts/gate.sh --root <repo> --json [--race] [--bench='^BenchmarkX$']` |
| TS/JS（有 `package.json`） | `bash <plugin_root>/skills/ts-gate/scripts/ts_gate.sh --root <repo> --json [--build]` |
| 两者都有（monorepo） | 各跑一次；改动所在那侧必须全绿，另一侧若被波及也要跑 |
| 都没有 | 跳过门禁，并在报告里写明"本项目无可用门禁"——**不得**用模型自评代替 |

- `ok=false` → 读 `log_dir/<stage>.log` 尾部，回到 3b 修复。**不得通过修改或删除测试、加 `@ts-expect-error` / `eslint-disable` 来变绿。**
- `arch` 阶段失败（跨层依赖 / 未分层新包）→ 回 3b 把依赖方向修对；**不得**用 `--skip arch`、放宽 `allow`、往 `ignore` 加路径来变绿——那是删判据不是改代码。确需新的依赖方向时，改 `.arch.json` 并在报告"未解决"里写明理由与影响面，交用户确认。
- `arch_verify` 失败（前缀匹配不到包 / 包多命中 / strict 路径写错）→ 错在契约不在代码：改 `.arch.json` 本身，并在报告里写明"原契约有 N 处失效规则，已修"。这类错不会让 `arch` 变红，若放着不管，之后每一轮的分层判定都是假的。
- `arch` 阶段 skip（仓库无 `.arch.json` 或缺 python3）不算通过，报告里如实写"未判定分层"，不要说"架构没问题"。
- 连续 3 轮门禁失败 → 停止循环，报告"方向假设错误"，不要继续换参数重试。
- 阶段 0 声明要做性能优化时：Go 项目 `--bench` 是强制的；TS 项目的 `--bench` **不产出 metric**，此时本轮不得标记为 `perf`，只能标 `feature` 或 `refactor`。

### 5. 审阅（独立子代理）

派发一个**独立上下文**的子代理，输入四样：`git diff <base>...HEAD`、验收标准清单、本轮假设、**项目全局契约**（`AGENTS.md` 的架构条目 + `.arch.json` 的层表与 allow 矩阵；两者皆无时明确告知"本项目未声明架构契约"）。要求其输出 JSON：

```json
{
  "blocking": [{"file":"x.go","line":42,"issue":"...","why_it_breaks":"..."}],
  "arch_drift": [{"file":"x.go","line":12,"from":"domain","to":"infra","rule":"allow[domain] 不含 infra"}],
  "advisory": [{"file":"x.go","line":88,"suggestion":"..."}],
  "clean": false
}
```

主会话必须**逐条验证** `blocking` 是否真实（读对应代码路径），再决定是否修。规则：

- 只接受能指出具体文件与行、且能说明"在什么输入下会错"的发现。
- 审阅发现的 `file:line` 是证据坐标，绑定本次 diff 的代码基线（写入阶段 7 报告的 `<branch>@<rev>`）；后续轮次行号变了也不回填旧发现，需要新坐标就新开一条发现。
- 拒绝：推测性风险、要求大范围重写、与需求无关的改进建议。
- `blocking` 修完必须重跑门禁（阶段 4），修改后不重跑等于没修。
- **`arch_drift` 非空即按 blocking 处理，不适用"结构问题延后"。** 越界依赖今天能跑，但每多一条，下次改动要读的包就多一圈，最终整个模块都动不了。修法只有两种：把依赖倒过来，或按 go-gate 的规则改契约并拿用户确认——两者都不做，就是违规保留。
- **契约缺失时 `arch_drift` 必须是空数组**，并在报告里记"无契约可对"。禁止让子代理"按常识判断分层"：那产出的是模型的偏好，不是项目的约定，据此提的修改建议会与项目实际分层直接冲突。
- `arch_drift` 与 `arch` 门禁结论冲突时（门禁过、子代理报越界，或反之）**以门禁为准**，并把该条记为"契约未覆盖的方向"，属于契约本身的缺口，进"未解决"让用户补规则。

**区分 blocking 的两种性质**，处置方式完全不同：

| 性质 | 例子 | 处置 |
|---|---|---|
| **缺陷**：当前输入下会出错 | 边界未处理、错误未传播、并发竞争 | 本轮修，重跑门禁 |
| **结构**：现在不错，但改下去会变难 | 函数过长、条件嵌套 5 层、同一逻辑散落三处 | **本轮不修**，登记为下一轮 `refactor` 目标候选 |

这张表里的"结构"指**局部写法**问题：不改就不出错，也不会封锁后续需求。**跨层依赖、循环依赖不属于此类**——它们不封锁单次改动，但会随需求累积把模块变成改不动的结构；架构层的问题必须当轮处理（见上方 `arch_drift` 规则）。

把结构问题塞进当前轮修，会同时违反"每轮一个假设"和"只改与该假设相关的代码"两条——事后指标变了无法归因。若结构问题严重到本轮无法在此基础上实现，正确动作是**作废本轮**（不记 keep/revert），退回阶段 2 重新切片。

确需在本轮做结构改进时（即本轮目标本就是 `refactor`），按需抽取 `refactor` 的对应手法，不要整份读：

```bash
grep -n '^### ' <plugin_root>/skills/refactor/SKILL.md    # 定位手法章节（Composing Methods / Simplifying Conditionals …）
# 再按行号抽那一节，约 30-80 行
```

`refactor` 的"行为不变 + 小步 + 测试守门"原则与本循环的判定机制一致：结构改动的正确性由门禁（`go-gate` / `ts-gate`）的测试结果证明，而不是由审阅者声称"改完更清晰了"。

### 6. 判定与结算

**判定必须由 `loop` 技能给出，不由本会话自行裁定。** 编排层只提供输入：指标值与本轮目标。

```bash
LOOP=<plugin_root>/skills/loop/scripts/loop.sh
V=$(bash $LOOP decide "$METRIC" --goal="$GOAL")   # KEEP | REVERT | INVALID | BASELINE
```

| 门禁 | 审阅 blocking | loop decide 输出 | 动作 |
|---|---|---|---|
| fail | 任意 | 不调用 | 记 `gatefail`，回 3b（不判定） |
| pass | >0 | 不调用 | 未完成，回 3b |
| pass | 0 | `KEEP` | `loop keep <round> <metric> "<假设>" <goal> --hyp="<假设>" --next="<下一步>"` |
| pass | 0 | `REVERT` | `loop revert`，并 `loop record <round> revert <metric> PASS <goal> "<假设>" --hyp="<假设>" --rollback="<为何放弃>"` |
| pass | 0 | `INVALID` | **停止循环**，报告"指标抽取失败"，不得重试同一命令 |

commit message 由 `loop keep` 生成：`dev(round N): <假设> [<metric>=<value>]`。**revert 行必须带 `--rollback`**——代码被回滚后，弃用理由是唯一存活的记忆，下一轮选假设前先读它（`loop report` 的"弃用方向与理由"一节）。

每次结算后同步写 `run.json` 的 `rounds_done`、`history`、`metric.best`、`updated_at`——它记录**流程走到了哪**，指标账本以 `.dev/results.tsv` 为准，两者不得互相覆盖。

### 停止条件（由脚本判定，不由模型判断）

每轮结算后执行一次：

```bash
bash $LOOP next     # CONTINUE <n> | STOP:target | STOP:no_improve | STOP:gate_failures | STOP:doom_loop | STOP:max_rounds
```

收到 `STOP:*` 即进入阶段 7，把停止原因原样写进报告。`STOP:doom_loop` 表示窗口内同一假设重复出现（原地打转或 A→B→A 震荡）——不要换个措辞重提同一假设，必须换结构性不同的方向。另有三条脚本无法判断、需编排层检查的停止条件：`stop_after` 在阶段边界命中（见阶段 1/2）、全部 `criteria.done=true`、以及用户中断。前一条走阶段 7 的"提前停止"分支，后两条走完整收尾。

## 阶段 7：收尾

### 提前停止分支（`stop_after` 命中）

由阶段 1 或阶段 2 的停止检查进入。此时没有执行任何验收标准、没有门禁日志、没有 round commit，因此：

1. **跳过"工作树干净"检查**——设计/切片文档是预期新增文件（未提交属正常），但不得有业务代码改动。若存在 `.go` / `.ts` / `.tsx` 等源码变更，停止并报告"提前停止时不应有实现代码"，不替用户回退。
2. **不推送、不合并、不创建 PR**，与完整收尾一致。
3. 生成 `.dev/REPORT.md`，使用下方的**提前停止模板**，不要套用完整模板的验收/指标/轮次表——那三张表在提前停止时全为空，填"未执行"比留空表更有信息量。
4. 交付顺序：停止原因（`stop_reason`）→ 设计/切片产物路径 → 未执行的阶段清单 → 继续实现时需要补做的事（阶段 0 的验收标准仍有效，从 `stop_after` 的下一阶段恢复即可）。

### 文档同步（仅完整收尾分支）

**对账对象**：`run.json.doc_path` 指向的文档（含上一次 dev 产出的功能文档）；若为 `null` 则取本次阶段 1 产出的 `tasks/<id>-design.md`。两者皆无时，在报告里写明"无设计文档可核对"，不得直接省略章节。

**强制触发**：只要对账对象存在，完整收尾就必须对账，不等用户提醒。这覆盖两类场景——首次开发后同步本次设计文档；后续 dev（如性能优化）在需求里指定 `doc_path` 后，回写原功能文档，即使本次阶段 1 被跳过也要对账。

**对账范围**：只核对第三部分（实现契约）中应落地的条目——架构、数据模型、API 端点/请求响应/错误码、业务逻辑、安全与性能约束、测试策略映射——外加**全局契约**（`.arch.json` 的层表与 allow 矩阵、`AGENTS.md` 的架构条目）。第一、二部分（产品需求、设计取舍）不因实现细节变更而回写，除非实现推翻了 Rationale 中被弃方案的理由——那属于方向性变更，必须用户确认。

**历史文档的特殊约束**：对账 `doc_path` 指向的旧文档时，只回写**本次改动实际触及**的契约条目，不得根据"旧文档与当前代码的其他差异"顺手补全——那些差异属于历史欠账，只在报告的"未解决"里列出。例如性能优化只改了实现与性能约束，就不要顺带改 API 端点描述。

**产出偏差清单**：每条写契约条目 / 设计值 / 实际值 / 偏差原因 / 处置。重点检测：

- API 路径、方法、请求响应字段、错误码与设计不一致；
- 表结构、实体定义与设计不一致；
- US-N 验收标准的实现方式或测试映射发生变化；
- 出现设计文档未覆盖的新模块或新依赖；
- **全局契约对账**：本次新增/改动的 import 是否越出 `.arch.json` 的 allow 矩阵；是否新建了未定层的包；`.arch.json` 与 `AGENTS.md` 的架构条目是否被改动（改层表 = 方向性变更，必须用户确认）。设计文档只描述"本次需求怎么建"，全局层表描述"这个项目怎么分层"——两者都要对，缺一个就会在下一次需求里重新漂移。

条目数与偏差数必须写入报告，偏差数为 0 也要写。

**确认**：呈现偏差清单，一次性询问"是否回写设计文档？"，不逐条问。

- **事实性修正**（API 路径、字段名、错误码、表结构、测试映射）：建议回写，但仍须用户确认后才改；
- **方向性变更**（被弃方案被推翻、架构改变、新增模块、改动层表/allow 矩阵）：必须用户明确确认，不得自行回写；
- 用户说"你定" / "按常规" 时**默认不回写**，偏差清单留在报告里供事后决定。

**回写规则**（仅在用户确认后执行）：

1. 只改偏差涉及的条目，**不重写全文**，不扩写其他章节；
2. 在文档末尾追加一行同步记录：`> 实现后同步（YYYY-MM-DD）：<需求 slug>（<feature | perf | ...>），<N> 条偏差已更新`。多次同步**追加多行**，不覆盖旧记录；
3. **不自动提交、不推送**；改动作为工作树变更列在交付说明里。
4. **回写遵守代码引用口径**：活文档只写路径 + 符号，不写行号；路径改名则更新路径，路径频繁变动或已删除则降级为「rev + 符号」并注明基线，不再回填新路径；契约条目只写包名/接口名/端点名，不写坐标。历史报告中的旧坐标**保留原样**——回写设计文档不等于改写历史报告。

### 经验沉淀（仅完整收尾分支）

提前停止分支**不执行本节**——没跑过实现与门禁，没有真实踩坑可提炼。完整收尾**强制执行以下步骤**，不等用户提醒，不因"看起来没坑"而跳过。

**第一步：扫描证据源（强制）**。逐一读取下列源，逐项填写结论，不得留空：

| 证据源 | 提取什么 |
|---|---|
| `.dev/results.tsv` 的 revert / rollback 行 | 被弃用的方向与理由 |
| `.dev/gate/`、`.dev/ts-gate/` 的失败日志 | 门禁失败与修复过程 |
| `loop next` 的 `STOP:*` 原因 | 停止时的真实障碍 |
| 阶段 5 审阅中被拒绝的 blocking | 拒绝理由，是否暴露工具/环境陷阱 |
| `tasks/<id>-design.md` 的"待解问题" | 哪些假设在实现中被推翻或澄清 |
| 本次工具调用与环境异常 | 代理、权限、版本、路径等陷阱 |

六类源全部扫描后才允许判断是否有候选。即使结果为空，也要在报告里写出"已扫描源"清单及每类结论——**只写"无"视为未执行**。

**第二步：标注归属**（三选一）——

| 归属 | 判定标准 | 去向 |
|---|---|---|
| 项目 AGENTS.md | 项目特有的工具/环境陷阱、易错配置、仓库约定，其他 Agent 在该项目会重复踩到 | 目标项目的 `AGENTS.md` |
| skill 改进 | 通用工具坑，或可编码为 lint / 元数据标记 / 运行时检查 / 脚本的重复纠正 | 不写 AGENTS.md，在报告"下一步建议"提示改对应 skill（遵循 `principles` 的 encode-lessons-in-structure） |
| 不沉淀 | 一次性偶发、无法复现、已有文档覆盖 | 只在候选表里保留标注，不落盘 |

每条候选写四要素：现象 / 根因 / 规避动作 / 适用范围，填入报告的"经验候选"表。不要为凑数编造，但也不得因为"用户没提"而省略扫描。

**第三步：强制询问**。交付时必须呈现候选表（即使全部归为"不沉淀"也要呈现扫描结论），并一次性询问"是否写入项目 AGENTS.md？"，**不逐条追问**。用户答复（写入 / 否决 / 你定）逐条记入候选表的"用户答复"列。用户说"你定" / "按常规" 时**默认不写入**——保守处理，避免污染指令文件；候选仍留在 `.dev/REPORT.md` 供事后决定。用户否决后不再追问。

**第四步：写入规则**（仅在用户明确确认后执行）：

1. 只写**规则化条目**：`"<约束>——<一句理由>"`。例如：`Windows 安装走 install.ps1，不要用 install.sh（ln -s 失败退化为复制模式，改动不实时生效）`。禁止写"某天遇到…"式叙事、轮次号或时间点——AGENTS.md 是给 Agent 的指令文件，不是日志。
2. 写入前读取目标项目的 `AGENTS.md`（没有则新建，仅含一级标题与条目列表），做**语义去重**：已有等价条目则更新理由、不新增；相近条目合并。
3. **不自动提交、不推送**；写入的 `AGENTS.md` 作为工作树变更列在交付说明里。
4. 需要深度复盘或产出新技能时，提示用户走 `reflect`，不要在本节展开多角色评审——dev 只做"顺手记录 + 确认 + 写入规则"。

## 失败处理

| 现象 | 处理 |
|---|---|
| 起始工作树不干净 | 停止，请用户 stash 或提交；不得在脏树上开始 |
| `stop_after` 取值非法（非 null/design/slicing） | 回到阶段 0 向用户澄清，不猜测、不默认走满 |
| 提前停止但工作树有业务代码改动 | 停止并报告，不自动回退；请用户确认这些改动的归属 |
| `stop_after=design` 但阶段 1 被跳过 | 回到阶段 0 澄清设计文档的归属，不空手进收尾 |
| 起始门禁就失败 | 先修复到全绿再进入 round 1，作为 `round 0` 记录，不占 `rounds_max` |
| `arch` 门禁报警（跨层依赖 / 未分层新包） | 回 3b 修依赖方向；不得 `--skip arch`、放宽 `allow`、往 `ignore` 加路径。确需新方向 → 改 `.arch.json` 并请用户确认，列入"未解决" |
| 项目有明显分层但无 `.arch.json` | 阶段 0a 用 `check-arch.py --init` 生成初稿，逐条复核"反向依赖"清单；不要手写，也不要把现状全放行 |
| 子代理报 `arch_drift`，但项目无契约 | 该条作废，记"无契约可对"；不许凭印象补规则再据此提修改 |
| 第 3 轮起才发现架构早就被改坏（存量欠账） | 不在本轮修。改契约前先问用户，把清单写进"未解决"，清债走独立 `refactor` 需求 |
| 门禁返回 rc=2 | 环境问题（无 go / 非 Go 模块 / 无 package.json），停止并报告 |
| benchmark 抖动导致判定摇摆 | 提高 `BENCH_RUNS` 到 7；不要降低 epsilon 来"稳定"结论 |
| `loop` 报告基准漂移（drift 警告） | 停止比较新旧指标。有意变更基准 → `loop drift --set` 或重记 `baseline` 开新段；否则恢复基准。**改基准后继续比数字等于造假** |
| `loop keep`/`record` 被账本审计拒绝 | 审计输出说明账本与本轮矛盾（如 perf 轮 keep 未改善、轮次倒退）。修正本轮判定流程，不要绕过审计；历史行不得手工改写 |
| 需求需要改依赖 | 用 `--allow-mod-changes`，并在报告"未解决"中列明新增依赖及理由 |
| 子代理审阅返回空 | 视为 `clean`，但记录"审阅未产出发现"，不要伪造审阅结论 |
| 目标 AGENTS.md 已有等价条目 | 更新理由、不新增；相近条目合并，避免同一条约束重复出现 |
| 用户否决经验写入，或说"你定" | 不写入、不再追问；候选保留在 `.dev/REPORT.md`，事后可自行决定 |
| `doc_path` 指向的文件不存在或不是合并设计文档（缺三大部分） | 回到阶段 0 澄清，不猜测、不自动改路径 |
| 阶段 1 被跳过、`doc_path` 也为 null 却进入文档同步 | 在报告写"无设计文档可核对"，不得省略该章节 |
| `doc_path` 指向旧文档，但本次改动未触及其中任何契约条目 | 偏差数写 0，不写无意义的"回写"，也不顺手补全历史欠账 |
| 经验候选表只写"无"、未列已扫描源 | 判定为未执行，回到"经验沉淀"第一步逐项扫描后重填 |
| 历史报告中的代码坐标已失效（文件改名 / 行号漂移 / 被 revert） | 保留原坐标与报告头部的代码基线，不回填、不"修复"；需要新坐标就在新报告里写新的证据条目 |

## 反模式

- 宣称"性能优化完成"但从未运行 `--bench`。
- 用户声明 `stop_after=design` 后仍进入切片或实现——停止检查在阶段边界强制执行，不因"顺手就做了"而跳过。
- 提前停止时套用完整收尾模板，产出空的验收表/指标表/轮次表，让人误以为执行过。
- 把"某天遇到…"式踩坑叙事、轮次号或时间点写进 AGENTS.md——那里只能放规则化条目，否则指令文件会膨胀成日志。
- 未经用户明确确认就写入 AGENTS.md；或用户说"你定"时擅自写入——默认不写入。
- 把通用工具坑写进项目 AGENTS.md，或把可编码为 lint / 脚本的重复纠正只写成文字——前者应改 skill，后者应遵循 encode-lessons-in-structure。
- 等用户提醒才做文档同步或经验沉淀——两者都是完整收尾的强制步骤，不是可选增强。
- 经验候选表只填"无"而不列已扫描源；或文档同步章节整节省略——视为未执行收尾。
- 文档同步时重写设计文档全文，或未经用户确认就回写方向性变更（架构、被弃方案、新增模块）。
- 自行推断 `doc_path` 指向哪份历史文档——对账对象是方向性决策，必须由用户明确指定或选择。
- 对账旧文档时顺手补全"与当前代码的所有差异"——只回写本次改动触及的条目，历史欠账进"未解决"。
- 把历史报告里失效的代码坐标回填成当前行号——历史坐标绑定报告头部的 rev，改了等于改写历史；复现靠 checkout 基线。
- 在活文档（设计稿、架构图）或契约章节里写行号——活文档留路径 + 符号，契约写包名/接口名/端点名，维护成本超过导航价值时降级为「rev + 符号」。
- 一轮内同时做重构 + 修 bug + 调优，事后无法归因。
- 指标退化仍保留改动（"虽然慢了但更清晰"）——清晰度应作为独立轮次的 `refactor` 目标。
- 用子代理的审阅结论直接替代验证（子代理也会臆断；blocking 必须逐条验真）。
- 把跨层依赖当"结构问题"延后——它不会自愈，只会随需求累积到改不动；架构层问题必须当轮处理。
- 用 `--skip arch`、放宽 `allow`、往 `ignore` 加路径让分层门禁变绿——这是删判据，不是修代码。
- 项目没有契约时让审阅子代理"按常识判断分层"——产出的是模型偏好，与项目实际约定冲突。
- 每个需求都重新描述一遍架构，却不更新全局层表——架构会从"契约"退化成"对现状的复述"，漂移被逐次固化。
- 循环末尾"抢救"部分被 revert 的代码，导致工作树与 `run.json` 不一致。
- 把 `rounds_max` 设成 20 期待"跑满就好"——收敛靠判据，不靠轮数。
- **每轮开头把 `modern-go` / `refactor` / `smell` 整份读进上下文。** 35k tokens 读进去却只用上一条规则，等于把后续轮次的预算提前烧掉。
- **以 `refactor` 为名夹带行为变更。** 该目标的判据只有"测试全绿 + 指标不退化"，测试覆盖不到的行为改动会静默通过。
- **在 `feature` 轮里顺手执行 `smell` 报告中的架构改造。** 那不是本轮假设的一部分，混进去就无法判断指标变化由谁造成。
- **使用 `modern-go` 索引中标为"不可用"的规则。** 会在项目声明的 Go 版本上直接编译失败，而门禁只会说"编译错了"，不会说"用错了版本"。

## 交付物

```
.dev/
├── run.json          流程状态（阶段、验收标准、每轮假设、stop_after/stop_reason、doc_path 对账文档路径；可 gitignore）
├── loop.conf         判定参数（epsilon / 轮数上限 / MEASURE_CMD 漂移检测对象；应提交）
├── results.tsv       判定账本（每轮指标、判决、ASI、commit，由 loop 维护并审计）
├── measure.cksum     基准指纹（gitignore，由 loop baseline 锁定）
├── hooks/after.sh    迭代钩子（可选，应提交；loop 每次记账后调用）
├── smell.md          存量诊断报告（可选，仅阶段 0.5；后续轮次读它而非重读源码）
├── tasks/<id>.md     切片（可选）
├── gate/<ts>/        每轮门禁日志（由 go-gate 写入）
├── ts-gate/<ts>/     同上，TS/JS 项目（由 ts-gate 写入）
└── REPORT.md         人读报告
tasks/                产品需求与设计文档（阶段 1；仓库根目录下，被 git 跟踪）
└── <id>-design.md    一份合并文档：产品需求 + 设计取舍 + 实现契约
AGENTS.md             项目级 Agent 约定（**阶段 0a 必读**；收尾经用户确认后写入/更新，不自动提交）
.arch.json            全局分层契约（**仓库根、入库**，不放 .dev/；阶段 0a 必读、`arch` 门禁据此判定；改动属方向性变更）
dev/<slug> 分支       N 个（或更少）round commit
```

`tasks/` 是过程产物的归属地，不搬到 `docs/`、也不复制副本——`docs/` 面向最终用户与团队，是稳定发布物的位置；设计文档会随实现反复修订，放 `docs/` 会混入中间态。仓库根 `.gitignore` 只忽略 `.dev/`，所以 `tasks/` 下的文档天然被 git 跟踪，团队可见可 review。需要归档到 `docs/` 时由人决定，且是移动而非复制，避免两份副本漂移。

`AGENTS.md` 位于**目标项目根**（不是 `.dev/` 下），内容是规则化条目而非经验叙事。它是**双向的**：阶段 0a 开工前必须读（架构约定、禁止依赖、易错配置），收尾经用户确认后可写入或更新；写入前须与已有条目语义去重。写入不自动提交。它是团队共享的 Agent 指令文件，与本地不入库的 `.workbuddy/memory/` 工作日志用途不同，不要混为一谈。

`.arch.json` 是**全局契约**，与 `tasks/<id>-design.md` 的分工不能混：设计文档说"本次需求怎么建"，`.arch.json` 说"这个项目允许谁依赖谁"。前者一需求一份、会随需求增多；后者全项目唯一、必须稳定。只有后者能阻止"每个新需求都把架构重新描述一遍"的漂移。**它放仓库根并入库，不放 `.dev/`**——`.dev/` 被 gitignore，只服务单次需求的过程记录（`run.json`、门禁日志、`smell.md`、`REPORT.md`），契约放进去就变成"本机约定"，CI、其它机器、后续需求都继承不到。非 Go 项目目前没有对应的确定性门禁，阶段 5 的审阅子代理按同一份层表判定，并在报告里标注"分层由审阅判定，非门禁判定"。

`run.json` 中的 `metric.epsilon_pct` / `target` / `rounds_max` 是 `loop.conf` 的**镜像**，用于让人在流程状态里一眼看到判据；实际判定一律以 `loop.conf` 为准，改判据只改那一处。
